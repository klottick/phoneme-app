# SQLite Learning Storage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the three learning families' preferences documents with one fresh, normalized SQLite learning database on native and web while preserving their existing domain transitions, progress views, and supported course-sync contract.

**Architecture:** A single lazily opened Drift database uses app-private SQLite on native and Drift's Wasm database on web. One shared SQL transaction coordinator performs receipt-first idempotency, scope-revision compare-and-swap, owner fencing, and atomic writes; three typed SQL adapters map the existing course, comparison, and sentence-hunt state to normalized rows while their pure transition engines remain authoritative. Providers switch all three families together only after the adapters are ready; no preferences learning writer, import, fallback, or second active store remains.

**Tech Stack:** Flutter 3.41.9 / Dart 3.11.5; proposed compatible pins `drift 2.34.0`, `sqlite3 3.7.1`, `drift_dev 2.34.0`, `build_runner 2.15.1`; Drift-generated schema and typed tables; `NativeDatabase` on native; `WasmDatabase.open` on web; existing Riverpod providers and pure Dart learning transitions.

**Spec:** `docs/superpowers/specs/2026-10-18-sqlite-learning-storage-design.md` (published and approved; the status line in that historical snapshot does not indicate a current approval gap).

## Global Constraints

- Fresh progress only: old preferences keys/data stay untouched; runtime does not read, import, migrate, dual-write, delete, or fall back to them.
- Use one `phoneme_learning.sqlite` file per native installation and one `phoneme_learning` SQLite database per web origin; all three families share it and are isolated by `(owner_kind, owner_id, course_id, family)`.
- Course, comparison, and sentence-hunt score, lesson, audio, completion, and lifecycle behavior remain unchanged. Persist only bounded typed checkpoints as JSON; never serialize attempts, aggregates, or full learning history as one database value.
- Schema version 1 is explicit. Only ordered, forward, atomic SQLite migrations may be added later; unknown/newer versions and failed upgrades remain untouched and unavailable.
- Web may use only Drift implementations `opfsShared`, `opfsLocks`, or `sharedIndexedDb`; reject `unsafeIndexedDb` and `inMemory`. No in-memory, localStorage, SharedPreferences, or other fallback is permitted for learning data.
- Every learner command atomically commits typed attempt/value/evidence rows, checkpoint, receipt, aggregates, completion/exposure/best-score changes, and any existing supported outbox rows. A failed/unknown commit is unavailable/retryable, never a successful save or empty profile.
- Check a matching receipt before expected-revision rejection. A matching token plus identical canonical payload is a no-op duplicate; a changed payload is invalid; an unproven stale command conflicts.
- Persist at most 2,000 attempts and 2,000 command receipts per owner/course/family. Trim whole course attempt batches. Preserve each current run's latest receipt after receipt-history pruning. Keep summaries, mistakes, completions, and exposure independent of detail pruning. Cap each applicable aggregate collection at 4,096 identities and reject overflow atomically.
- Do not impose the historical 36 MiB serialized-document/codec limit as a SQLite database or row limit.
- Preserve `course_learning_sync.dart`'s exact current projection: supported course answer/lesson/score events only; unchanged `id`/`user_id`/`course_id`/`kind` envelope; unchanged answer fields; `record_course_events`; batches of at most 100; acknowledge delivered IDs. Add no comparison/sentence events or selected/expected answer, checkpoint, or full-attempt uploads.
- Keep guest/account identities distinct, account IDs exact (not delimiter-concatenated), and captured auth generation fenced, including A→B→A. An old in-flight write may affect only its captured owner and cannot notify a new owner's providers.
- A verified new database is empty only after successful open, schema setup, and query. Loading, open/query failure, corruption, quota denial, unsupported backend, and unknown version are not zero/not-started. Do not restore playback, hearing grants, timers, microphone state, or autoplay authorization.
- Keep `SharedPreferences` for unrelated settings/auth state if already used. Do not touch unpublished Sound Match work, course/audio/content approvals, licences, release gates, other worktrees, or durable evidence.
- Proposed dependency gate: raise only `frontend/pubspec.yaml`'s app lower SDK bound from `>=3.3.0` to `>=3.10.0 <4.0.0`; do not upgrade the installed Flutter/Dart SDK, force overrides, or silently choose another storage stack. Candidate package pins are inputs, not a solved package set. If the candidate cannot solve/generate/build, stop for a concrete revised decision.
- Real browser/native qualification is evidence, not inference. An unrun browser/device, storage-denial path, or unsupported runtime remains OPEN and blocks any support/capacity claim. Do not report runtime qualification from this plan.

## Review Focus

- A browser selects `unsafeIndexedDb` or `inMemory`, or the WASM/worker assets fail to load: fail closed before publishing learning state; never silently continue with volatile or unsynchronized data. Tests: Task 1 `learning_database_connection_web_test.dart` rejects each enum value; Task 1/8 actual browser smoke asserts the selected implementation and restart behavior.
- A same-token retry arrives after the scope revision advanced, or the token is reused with another payload: matching receipt must win before stale-revision rejection, while changed payload is invalid and an unproven pruned command conflicts. Test: Task 3 `learning_sql_transaction_test.dart`, `receipt_retry_precedes_stale_scope_revision_and_changed_payload_is_invalid`.
- A second connection/tab commits from the same snapshot, or an account switches A→B→A during work: one divergent writer conflicts without lost updates; captured work never crosses owner scopes or notifies the replacement provider. Tests: Task 3 `learning_sql_transaction_test.dart`, `independent_connections_commit_one_divergent_command`; Task 7 `learning_providers_test.dart`, `aba_write_stays_in_captured_scope`.
- A SQL statement fails after some candidate rows were written or the caller loses the commit acknowledgment: a reopened database shows the complete prior or complete committed state, never partial credit; exact retry creates one attempt. Test: Task 8 `learning_sql_recovery_test.dart`, `injected_sql_failure_rolls_back_and_lost_ack_retry_is_once`.
- A history/receipt limit trims a multi-answer batch or an aggregate collection reaches 4,096: preserve the latest checkpoint/receipt and cumulative summary; refuse overflow without dropping old aggregates or partially crediting. Test: Task 8 `learning_sql_retention_test.dart`, `all_families_reopen_at_limits_without_summary_drift`.
